# ADR-0010: Вход по SMS-коду, сессии Django через общий домен

- **Статус:** Принято
- **Дата:** 2026-11-10

## Контекст

По КП покупатель входит в личный кабинет по номеру телефона. Пароли покупателям не нужны. Фронтенд (Next.js) и API (Django) — разные процессы, и нужно безопасно хранить вход в браузере.

## Решение

1. **Один домен.** Next.js проксирует `/api/*` и `/media/*` на Django (rewrites). Для браузера API живёт на том же домене, что и сайт.
2. **Сессии Django.** Cookie `sessionid` — `HttpOnly`, `Secure`, `SameSite=Lax`. Для изменяющих запросов залогиненного пользователя — CSRF-токен в заголовке `X-CSRFToken`. Токены не лежат в localStorage, поэтому XSS не может их украсть.
3. **Вход по одноразовому коду:**
   - `POST /auth/otp/request/` — 6-значный код. В БД хранится только HMAC-хеш кода.
   - Код живёт 5 минут, на один код даётся 5 попыток.
   - Повторная отправка — не чаще раза в 60 секунд и не больше 5 раз в час на номер.
   - `POST /auth/otp/verify/` — создаёт пользователя при первом входе и открывает сессию.
4. **SMS-провайдер подключается адаптером** (`SMS_BACKEND`). Сейчас код пишется в лог сервера. Провайдер (Eskiz, Play Mobile…) выбирается на этапе 06.
5. **Гостевые заказы.** После подтверждения телефона к аккаунту привязываются заказы, ранее оформленные на этот номер без входа.

## Альтернативы

| Вариант | Плюсы | Минусы |
|---|---|---|
| JWT в localStorage | Просто для SPA | Токен крадётся через XSS, сложный отзыв |
| JWT в cookie через BFF-слой Next.js | Безопасно | Свой слой авторизации в Next.js, больше кода |
| **Сессии Django + same-origin прокси** ✅ | Готовые механизмы Django (сессии, CSRF, выход), минимум кода | Все запросы API идут через Next.js |

## Последствия

- В продакшене достаточно одного домена и одного SSL-сертификата.
- `CSRF_TRUSTED_ORIGINS` должен содержать адрес сайта.
- До выбора SMS-провайдера вход работает только в разработке (код в логах).
